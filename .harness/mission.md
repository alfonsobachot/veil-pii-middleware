# Mission

## Objective

Make the gate blind to a sabotaged validator no longer possible. Insert
deliberate decoys into the demo corpus — check-digit values that are wrong on
purpose (DNI bad letter, card failing Luhn, IBAN failing mod-97) and non-PII
values that merely resemble PII (a Spanish thousands-separated figure, a
version string, a zero-padded account number) — recorded in the database but
absent from `demo/manifest.json`. Add a false-positive gate to `demo/eval.py`
with a concrete threshold and the exact listing of which decoys tripped it,
wire it into `.harness/bin/verify` next to the existing recall gate, and add a
test proving that sabotaging one of the three check-digit validators flips
that gate red.

The blind spot this closes: today `eval.py` only measures recall (does every
real PII instance get found) and an incidental precision figure scoped to
cells that already contain manifest'd PII. Nothing in the corpus currently
exercises the rejection path of `valid_dni`, `valid_card` or `valid_iban` at
the gate level — if one of those functions were changed to always return
`True`, recall would stay at a perfect 1.000 and the gate would stay green.

Enough to exercise each rejection path without inflating the corpus the mission explicitly kept small. |

## Scope

- `veil_pii_middleware/demo/seed.py` — `Decoy` dataclass, `_Corpus.decoys` /
  `note_decoy()`, the `decoy_samples` table, generators for the six decoy
  categories, `DEFAULT_DECOYS_PATH`, and writing `demo/decoys.json`.
- `veil_pii_middleware/demo/eval.py` — `DecoyHit`, `DecoyReport.exceeds()`,
  `evaluate_decoys()`, `--decoys` / `--max-false-positives` CLI flags, and the
  decoy section of the printed report.
- `.harness/bin/verify` — the `eval` gate row gains `--max-false-positives 0`
  next to `--min-recall 1.0`.
- `.gitignore` — `demo/decoys.json` joins `demo/manifest.json` as a generated,
  git-ignored artifact.
- `tests/test_demo.py` (or a new `tests/test_decoys.py`) — decoys absent from
  the manifest, zero decoy hits under normal operation, and a parametrized
  test sabotaging `valid_dni`, `valid_card` and `valid_iban` in turn to prove
  each one flips `DecoyReport.exceeds(0)` to `True`.
- `.harness/validation.md`, `.harness/handoff.md`.

## Non-Goals

- No change to `core/detector.py`: no new pattern, no new validator, no
  change to `merge_spans()` or `detect_regex()`. The sabotage test simulates a
  broken validator by monkeypatching `_PATTERNS` in the test, not by editing
  the module.
- No change to the existing recall/precision path in `evaluate()` — decoys
  get their own function and their own report, not a retrofit of `Metrics`.
- No raising the corpus volume beyond what the six decoy categories need.
- Do not weaken or remove the five pre-existing gate rows, nor the recall
  threshold on the `eval` row.
- No vault, tokenization, audit log or adapter work — unrelated to this
  mission.

## Acceptance Criteria

1. `demo/decoys.json` exists after seeding, lists every decoy with `table`,
   `column`, `row_id`, `offset`, `value` and `reason`, and shares none of
   those table/column/row_id/offset combinations with `manifest.json`.
2. Under unmodified `core/detector.py`, `evaluate_decoys()` returns zero hits:
   every decoy is correctly rejected.
3. `demo/eval.py --max-false-positives 0` exits non-zero if any decoy is
   detected, and the printed report names the concrete decoy (table, column,
   row id, value, reason) that tripped it — not only a count.
4. A test sabotaging `valid_dni`, `valid_card` or `valid_iban` (via a
   monkeypatched `_PATTERNS` entry, in isolation, one at a time) causes
   `evaluate_decoys()` to return at least one hit tied to that entity type,
   and `DecoyReport.exceeds(0)` becomes `True` for each.
5. `.harness/bin/verify`'s `eval` row runs `--max-false-positives 0` alongside
   `--min-recall 1.0`, and all six existing gate rows stay green.
6. Two consecutive seed runs produce byte-identical `demo/decoys.json`, same
   as the existing manifest determinism guarantee.

## Tooling And Approach Assessment

1. **What project type is this?** Continuation of the existing pure-Python
   detection/evaluation work: deterministic fixture generation plus a scoring
   script, no network or service surface.

2. **What methods, tooling, or approaches does that imply?** Reuse the
   existing `_Corpus` / `Instance` / manifest-writing pattern in `seed.py` for
   a parallel `Decoy` / decoys.json pipeline; reuse `_load_texts()` in
   `eval.py` since decoy cells are fetched the same way manifest cells are;
   `pytest.monkeypatch` against the module-level `_PATTERNS` tuple to simulate
   a sabotaged validator without editing `detector.py` — `detect_regex()`
   resolves `_PATTERNS` as a module global at call time, so rebinding the
   module attribute takes effect without touching the function objects
   themselves.

3. **What risks or missing decisions does it reveal?**
   - A false positive on a decoy is only detectable if `eval.py` looks at the
     exact cell the decoy sits in; the new dedicated `decoy_samples` table
     avoids any ambiguity with the real corpus's existing manifest'd cells.
   - The DNI/card/IBAN decoys must be generated to *deterministically* fail
     their check digit under the current seed — verified at generation time
     the same way `seed.py` already asserts real instances pass theirs (invert
     the assertion: raise if a generated decoy accidentally validates).
   - `valid_international_phone`'s zero-padded-account decoy is a length-floor
     check, not a checksum; it is still included as a decoy (a regression
     guard) but is not part of the three-validator sabotage test the mission
     names explicitly, since it has no check digit to sabotage in the same
     sense.
   - Monkeypatching a private module tuple (`_PATTERNS`) from a test is a
     deliberate simulation of "a validator silently regresses in place," not
     a supported public API; if `detector.py`'s internal structure changes
     later, this test's setup — not its intent — will need updating.

4. **What should be added to validation?** The `demo/decoys.json` /
   `manifest.json` disjointness check; a zero-hits-under-normal-operation
   check; the parametrized three-validator sabotage test; confirmation the
   `eval` gate row change is additive (recall threshold untouched); decoy
   determinism across two seed runs; confirmation the five pre-existing gate
   rows are unmodified.

5. **What is explicitly not needed now?** Any change to detection logic
   itself, any new entity type, any change to the manifest schema, any
   increase in corpus volume beyond the twelve decoys, and no touching of
   `core/tokenizer.py`, the vault, the audit log, or any adapter.

## Risk

Risk class: high

Same high-risk surface CLAUDE.md names for detection and the gate, even
though `core/detector.py` itself is untouched: this mission changes what the
gate is capable of catching, and a mistake here (e.g. a decoy that
accidentally *is* detectable today, or a threshold wired to the wrong flag)
would either produce permanent false alarms or silently fail to close the
blind spot it exists to close. Protected areas: the five pre-existing gate
rows, the recall threshold on the `eval` row, and `core/detector.py` itself
must not be modified.

## Merge Policy

High-risk human verification required. Independent `goal-verifier` and
`code-reviewer` passes before merge. A security-focused review pass is
warranted: this mission's entire point is proving the gate detects a
regression in code that decides what counts as sensitive data.
